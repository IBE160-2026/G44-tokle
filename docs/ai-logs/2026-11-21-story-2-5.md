## 4. Bugs found in the AI's code

**Before the review**, the AI broke each new rule on purpose (24 changes) and checked that a test failed. This took three runs:
1. **Edvard's PC shut down during the first run.** The check edits the source files one at a time, and Edvard asked the AI to make sure no planted break was left behind before anything else. The AI checked every planted spot: one break was still in the code (the job claim said "not queued" where it should say "queued"). It was restored, all tests passed, and at Edvard's request the work was committed so it could not get lost.
2. **The second run hung** (Edvard noticed it had taken 20 minutes instead of 8). The planted break made every claim fail, and the function that picks the next job then looked again for ever. In the real app that cannot happen, but the AI offered two fixes: change the code so it tries each waiting job once and then gives up until its next look (A), or only put a time limit on the check (B). It recommended A; **Edvard chose A**. A test now covers it, and each check run has a 2-minute limit.
3. **The third run missed 2 of 24**: the tests measured "24 hours" with the 24-hour constant itself, so a change to 48 hours passed them; and nothing checked that the fetching dots stop with *reduce motion*. A test was added for each, and both now fail when broken.

While re-reading its own diff, the AI also found that moving an upper-case address to lower case passed on every query parameter, so a strange URL could crash the page; it now keeps only the two the page uses.

**The three reviewers** raised 31 findings. The AI checked each against the code:

| Found by | Problem | Fix |
|---|---|---|
| All three reviewers | Reloading the "Polymarket did not answer" page never tried again, though the page says "Try again in a few minutes." | A reload more than 60 seconds after the failed fetch starts a new lookup (AI's suggestion; **Edvard confirmed 60 s**) |
| Blind and edge-case reviewers | If the fetch finished just as the page was reading, the page could start a second, needless fetch | The page reads the job first, then the stored data |
| Blind and edge-case reviewers | Ending a job did not check that it was still running; an interrupted job still said "Fetching…" | Fixed, with tests |
| Blind and edge-case reviewers | A failed lookup's error page came back as a success (HTTP 200) | Now 500, like the app's other error page |
| Blind reviewer | Two page texts were written in two places | Each written once |
| Verification-gap reviewer | Nothing tested that the background thread survives an error, or that a new job wakes it at once, or the outage pages once fresh data exists | Tests for each; the first wake test had its own timing race and was rewritten |

The AI broke each of these fixes on purpose too: two of the new tests did not bite at first and were rewritten until they did. One finding is deferred: the new JavaScript runs in no automated test, because the project has no JavaScript test setup (Edvard's browser check covers it for now). The rest were rejected with reasons, for example "job rows are never deleted" (about 100 bytes per lookup on one laptop). The full table is in the spec's Review Triage Log.
