## 3. Planning Story 6.1

The AI wrote the epic's summary file (`epic-6-context.md`) and investigated before drafting the spec. Three things it measured rather than assumed:

- **The stored Scan** (read from the kept copy, read-only): both Scans are stored as finished, all 200 Wallets still have their bets after the date, 118 Wallets have 10 or more of them, and at most 9,644 bets need a price. So the Copy Test needs nothing from the Scan fetched again, only prices.
- **The old price route** still gives one-minute points: 60 for the daily check's hour, 19,615 for a 14-day window.
- **The replacement route** (`/v2/prices-history`): the AI did not know its details and probed it. It takes other parameter names than the plan's text suggested (`token_id`, `start`, `end`; it refused `market=`), each row says how coarse it is, and it gave **nothing** for July 2025. So if the old route is switched off before Story 6.6, a Scan with the default Cut-off Date gets no prices, and the 50-Wallet insurance pool from October is the only way, as the plan already says.

The risk the AI pointed out for Edvard's requirement: the story adds two database tables, and the app converts an older database file when it starts. That conversion was only ever tested on small files, never on the 1.1 GB live database. The spec therefore says: convert a **duplicate** of the kept copy first, compare it with the kept copy, and do not start the app on the live database with the new code before that passes.

The AI asked three questions, each with a recommendation:

1. **How does a finished Scan get its Copy Test?** (a) a "Run Copy Test" button on a finished Scan that has none, or (b) the app starts it by itself when it finds such a Scan. The AI recommended (a), so the user decides when about 10,000 price requests start. **Edvard chose (a).** It is built in Stories 6.2 to 6.4 and written into the plan now.
2. **Helpers** (fresh AI sessions). **Edvard chose review only** (AI rec), as in the five stories before.
3. **Spec size**, about 2,600 tokens against BMAD's guide of 1,600. **Edvard kept it whole** (AI rec).

His answer: "1a 2 yes 3 keep whole, approve and continue". The decisions went into `epics.md` (Epic 6 and Story 6.1), the architecture's AD-5, AD-6 and AD-24, and two memlogs before any code was written.

Choices the AI made itself, shown in the spec he approved:
- How the app knows the old route is still good: it sends the daily check's own request before using the route and again after an hour, and judges the answer by the check's own rule. A test runs the workflow's script and the app's rule on the same answers and requires the same result, so "the daily check alerts" and "the app leaves the old route" are the same event.
- Only a definitive answer is stored. If Polymarket does not answer, nothing is stored and the job stops with Resume, as for every other read.
- On the host that also takes orders, the app's URL guard lets exactly one address through: the price history.

## 5. Review

Three fresh AI helpers read the diff without the conversation: one looking for anything wrong or missing, one for edge cases, one for behaviour that no test would catch. They filed 41 findings (16, 18 and 7). The AI checked each against the code before deciding.

**What they found that mattered.** The serious findings were one fault seen from three sides: the app could leave the old price route, or store "no price" for good, on too little evidence. Because stored prices never expire, each of these would have quietly emptied part of a Copy Test:

| Found by the helpers | What would have happened | Fix |
|---|---|---|
| One "not found" answer for one token made the app leave the old route for an hour | Every later token asked of the new route, which has nothing for 2025; their empty answers stored for good | It now only triggers the route check again, like a thin answer |
| A route-check answer in an unexpected shape counted as "empty" | The same | It now counts as unreadable and stops the job, which can resume |
| A block by Polymarket (403 and similar) was stored as "this token has no price" | A blocked run would have "finished" with every price missing | A block now stops the job like an outage; nothing is stored |
| The route check was repeated only once an hour | A whole Copy Test fits inside an hour, so a route that changed mid-run would not be noticed | Also repeated every 200 price requests |
| A stored window's label could be overwritten by a later request | "Where did this answer come from" would be wrong | Each asked window is its own row |

**Found on the way, in older code.** The code that converts the database (from Story 4.3) treated any database error while copying a Scan's stored bets as "the new layout does not fit" and then dropped them. A full disk in the middle of copying 1 GB would have done exactly what Edvard asked to avoid. It now gives up and leaves the file as it was. A test plants a "disk is full" error and checks the Scan is intact afterwards. This story is the first to run that code on a large file, which is why it surfaced now.

**Also fixed:** the offline price function refuses the same bad requests as the live one; the button "Run Copy Test" was only in three places of the plan and now has acceptance criteria under the stories that build it; 12 missing tests; a README paragraph about the first start after an update.

**Rejected (4)**, each with its reason in the spec's review log: for example a job that keeps stopping when the old route answers with a redirect for good (it stops loudly and can resume; the new route has nothing for 2025 anyway).

**Deferred (2, in `deferred-work.md`):** an older version of the app opening a newer database file drops the stored prices (an older rule; the advice until then is not to do that), and no test reads a real row of the new route (it needs a token traded this week).

**Two findings went to Edvard,** because the code now differs from the table he approved:
1. The table said an answer whose points are far apart "is not used". Built: it is used when the route check still passes.
2. The table said every refusal is stored as "no price". Built: a block is not stored; it stops the job.

The AI recommended yes to both: otherwise one odd token throws away its own good prices, and a block says nothing about the token. **Edvard accepted both** ("1 yes 2 yes, commit n push"). The table in the spec was changed by his decision, with an entry in the spec's change log; the code was not changed again.

## 6. What the AI got wrong, and how it was caught

- **Left the old price route too easily, twice.** The first version left it on one thin answer; the AI's own test caught that while building. The AI fixed that case and left the same hole open for a "not found" answer; two review helpers caught that one.
- **Stored a block as "no price".** Caught by all three helpers. The AI had written "only a definitive answer is stored" into the spec and then not applied it to a 403.
- **Said the approved table still held when it did not.** After changing the thin-answer rule the AI wrote in the spec's notes that the table row "holds as written". Two helpers pointed out it does not. The note is corrected and the question went to Edvard.
- **A guessed number in a test.** The AI expected 34 points in a 34-minute window; both ends count, so it is 35. Its own test run caught it.
- **A rule that cancelled another.** The first version of "check again after 200 requests" never fired, because "trust a check for a minute" came first and 200 requests take 40 seconds. The new test for it failed at once.
- **A long shell command with pasted code broke again**, as in earlier stories. Nothing had run; the AI wrote the edits to a script file and ran that, and did so for the rest of the session.
- **A time guess, flagged as one:** "about 35 minutes" for the live Copy Test's roughly 10,000 price requests is not measured.
